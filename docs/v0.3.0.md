2026-11-16。本地验收完成，未提交、未推送、未打标签或创建 Release。AI-01 实网和医护评估依然未完成。

## 使用流程

1. 管理员“排班与号源”→指定医生“排班变更”，选择停诊/替诊并填写原因。替诊必须选择其他已启用且关联该院区和科室的医生，时间冲突仍会拒绝。
2. 成功提交即关闭原排班并保存影响清单；“排班变更”查看处理进度和影响条目。每5秒轮询，单任务每批20条；可手动处理下一批。
3. 取消失败累计3次后显示失败摘要，核对数据后“重试失败项”。每条预约独立提交，成功项不被失败项回滚，不重复释放容量。
4. 替诊自动提供替代排班建议；停诊后也可按单条预约选择同院区、同科室的未来开放排班作为建议。
5. 患者“变更通知”查看原因及原预约处理状态，查看新医生和时间、选择新时段并勾选同意。提交成功才占用新号源；满号或目标停诊时可联系机构更新建议。患者可以拒绝，不会被自动迁移。

## 数据与配置

Flyway V4 增量添加排班状态、任务和任务条目，不重建旧表、不新增 CHECK。启动前建议保留数据库备份，迁移只随新版后端正常启动执行。请勿修改已应用迁移；回到旧应用版本不能视作数据库回滚。

后端 `yiyue-application/src/main/resources/application.yml`：`CHANGE_WORKER_ENABLED` 默认true，`CHANGE_POLL_MS` 默认5000。关闭轮询时管理员仍可手动处理。进度保存在PostgreSQL，不依赖Redis任务队列；Redis继续承担会话。无需新依赖或第三方账号。

API：

| 角色 | API | 用途 |
|---|---|---|
| 管理员 | POST /api/admin/schedules/{id}/change | 发起停诊/替诊 |
| 管理员 | GET /api/admin/changes、/{id}/items | 任务与影响清单 |
| 管理员 | POST /api/admin/changes/{id}/process、/retry | 分批处理、重试失败项 |
| 管理员 | POST /api/admin/changes/items/{id}/proposal | 提供改约建议 |
| 患者 | GET /api/patient/changes | 自己提交预约的变更通知 |
| 患者 | POST /api/patient/changes/{id}/accept、/decline | 明确确认或拒绝建议 |

写请求要求真实会话CSRF。患者只能操作自己账号创建的预约；同机构其他患者和跨机构访问均受限。审计记录排班变更、取消、重试、建议、确认和拒绝。

## 范围与限制

- 已开始排班和存在已签到预约的排班不能停诊，需另行处理现场业务。
- 原排班永久关闭，本版本没有“撤销停诊”。相同变更重复请求返回原任务；不同方式/不同替诊医生返回冲突。
- 新排班不提前锁定号源；原预约取消与患者接受建议是两个独立业务阶段。
- 系统内通知，不含短信、邮件、候补、支付或退款；后续按版本计划推进。
- 最近100个任务/患者通知，单任务影响清单整体加载；机构级锁串行写入，医院级吞吐未压测。
- 轮询器重建恢复可测试，操作系统强杀恢复、Docker实机、远程CI未在本轮验证；DeepSeek实网与医学评估仍待外部条件。
